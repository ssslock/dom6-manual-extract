# Dominions 6 manual → structured Markdown

Extracts the **text layer** of the Dominions 6 manual into per-chapter Markdown,
preserving heading hierarchy, paragraph boundaries, and tables as real Markdown
tables. No OCR, no LLM, no cloud API. Fully deterministic: same input PDF →
byte-identical output.

Built for RAG / LLM use, where the useful unit is not "the manual" but
"a paragraph or a table row that answers a question about game mechanics".

---

## Why not just `pdftotext` or an OCR pipeline?

Because both fail on this document in ways that are invisible until you read the
output.

**Naive text extraction** returns lines in the wrong order. The manual is laid out
in two columns on 169 of its 449 pages. The single most intuitive sort —
`y` then `x` — interleaves the columns and produces sentences stitched from
opposite sides of the page:

```
Some items are restricted ... battlefield spells. These items don't show ...
```

Also: paragraph gaps and line gaps are not distinguishable from the raw text
(`\n` everywhere), and tables come out as a flat token stream.

**OCR** (we tried a VLM-based document model) reads the page as an image and
writes one continuous stream. Layout is recognised, but *structure is destroyed*:
a 20-page summoning table with 6 columns becomes 195 KB of `F1E1 9 Terracotta
Soldier x15+ Conj 2 Summon Fire Ants ...` on a single line. Recovering the column
boundaries afterwards means guessing, and the contents are numbers (gem costs,
HP, levels). Guessing a number is hallucination.

**This PDF does not need OCR.** It is generated by *Haru Free PDF Library 2.3.0*
— a native, programmatically typeset PDF with a complete text layer. The
characters are read out of the file, not recognised from pixels.

## Key findings about this specific document

1. **The page content stream is already in reading order.** The typesetter writes
   column by column, so PyMuPDF's default (unsorted) block order *is* the correct
   order. Sorting by coordinates is what breaks it. Verified on p.81: default
   order gives a correct sentence spanning both columns, `y`-then-`x` does not.
2. **Font size carries the entire hierarchy.**
   `14.2` chapter / `12.4` section / `11.4`+`10.4` subsection / `9.5` body /
   `8.6` table cells, formulas and bullet lists.
3. **Bookmark depth is more reliable than font size.** The PDF has 407
   bookmarks. Same title can carry different levels on different pages
   ("Magic" is h3 on p.32 and h1 on p.73), so bookmarks are matched on
   *(title, page)* pairs.
4. **Paragraph break == vertical gap.** Within a paragraph the leading is
   `14.2pt`; between paragraphs `24.2pt`. Across 93 pages there is nothing in
   between — the histogram is bimodal, so a threshold at `14.2 × 1.45` is safe.
5. **Tables are runs of 8.6pt lines whose cell `x` values cluster into columns.**
   Column origins are exact to 0.1pt. A row missing the first column is a
   wrapped continuation of the row above it, not a new row.

## Verification

The claim being checked is: *no text is lost or invented.*

Both sides are tokenised (`[A-Za-z0-9]+`) and compared as multisets, after
removing (a) the page-number footers from the PDF side and (b) the `<!-- p.N -->`
page markers + per-chapter subtitle lines that the extractor adds:

```
PDF  (p.6–98) : 61,485 tokens
Markdown      : 61,485 tokens

missing from md : 2   'Turn', 'Effects'
not in pdf      : 2   'TurnEffects', '32'
```

That single difference is a cell spanning two rows in the p.71 *Twilight* table
(see *Limitations*): `Turn` + `Effects` are merged into `TurnEffects`, and one
row value (`32`) lands outside the table. **Zero words lost, zero invented.**

### Check it yourself

Don't take the number above on trust — it is reproducible, and you should
reproduce it on your own copy of the manual:

```bash
python validate.py --pdf dom6manual.pdf --md chapters --expect-known-delta
```

It prints both token counts and the full list of differing tokens. `--expect-known-delta`
accepts **exactly** the p.71 artefact and nothing else: the allowlist is an exact
multiset comparison, not a fuzzy match, so any additional difference — a dropped
word, a duplicated row, a wrong number — makes it exit non-zero. Without the flag
it is a strict equality check.

If it fails for you, that is a real finding. Open an issue with the output and
the page number (see [`CONTRIBUTING.md`](CONTRIBUTING.md)) so the offending
heuristic can be fixed.

Two other checks:

- **Reproducibility** — running the script twice produces byte-identical files
  (MD5 compared across all 9 chapters). No randomness, no model calls.
- **Table integrity** — every Markdown table has an identical number of columns
  in every row (0 ragged tables out of 49).

The PDF's own text layer for this range is 281,931 alphanumeric characters; the
Markdown carries 283,169 including the added `p.N` markers.

## Usage

Requires Python 3.9+ and PyMuPDF.

```bash
pip install -r requirements.txt

# The manual is distributed by Illwinter (see note below) — download it first:
#   http://ulm.illwinter.com/dom6/dom6manual.pdf

python extract_dom6.py --pdf dom6manual.pdf --out chapters
```

Options:

```
--pdf PATH      input PDF (default: ./dom6manual.pdf)
--out DIR       output directory (default: ./chapters)
--start N       first PDF page, 1-based (default: 6, skips the table of contents)
--end N         last PDF page, 1-based (default: 98)
--manifest PATH manifest.json location (default: next to --out)
```

Each chapter starts with `# Title` and `*Dominions 6 manual, p.N*`; every heading
and table carries a `<!-- p.N -->` comment so any paragraph can be traced back to
a physical page.

Then verify:

```bash
python validate.py --pdf dom6manual.pdf --md chapters --expect-known-delta
```

## Limitations

- **The p.71 *Twilight* table is incomplete.** Cells that span multiple rows
  (`TurnEffects`, and a stray `32`) end up outside the table. Reassembling
  row-spanning cells is a different problem from column detection and is not
  implemented. Contents are present, arrangement is not.
- **Page range.** Only p.6–98. The table of contents (p.1–5) and the spell,
  item and nation reference (p.99–449) are not extracted. Those sections are
  large multi-page tables with a different shape; if you need them, the same
  primitives should work but the row/column heuristics need testing there.
- **No images.** Text only.
- **Requires a real text layer.** A scanned copy of the manual would produce
  empty output — by design, rather than silently emitting garbage.
- Very rarely a sentence continuing across a column break starts with a capital
  letter (e.g. a proper noun such as *Ulmish masons*) and is treated as a new
  paragraph. This over-splits; it never loses text.

## Contributing

The most useful report is a **page number**. If you find text that is wrong,
missing, or in the wrong shape, run `validate.py` and open an issue with its
output plus the page — instructions, the four mandatory checks, and the
constraints any patch must respect are in [`CONTRIBUTING.md`](CONTRIBUTING.md).

The extracted Markdown is deliberately **not** published here (see *Copyright*),
so a reproduction means running the extractor on your own copy of the manual.
